What should happen when the player dies?

This is the one choice that decides almost everything else about the room/checkpoint feature — so let's look at it before anything else.

A — Pure roguelite (what CINDER LOOP has today, D1)
Spawn — fresh run, fresh stats
↓
Fight through the level
↓
Clear → Boss
↓
Die — anywhere, anytime
↓
Spend currency → brand-new run, brand-new level

One life per run. A death is never "reset to nearby" — it's the run ending. Progress that persists is only the meta-currency/blueprints (65-meta.js), never position.

B — Checkpoint resume (Castlevania / Hollow Knight)
Enter room
↓
Fight, clear the room
↓
Checkpoint lights up
↓
Die — anywhere after that point
↓
Respawn AT the checkpoint — same run continues

Death is a local setback, not a run-ending event. The "run" itself may not exist as a concept at all — more like one long expedition through the castle/game world.

Why this matters: D1 (this project's very first locked decision) says "the loop is the product... a biome without a death-and-spend cycle is a platformer demo." Model A is what's built and what 65-meta.js's currency/blueprint system assumes. Model B is what "hit a save point" usually implies in the games you named — but it changes what death MEANS, which changes the currency economy, the meta-progression pacing, and probably the pitch of the whole game.

A

Keep pure roguelite (D1 intact)

Rooms/checkpoints are PACING and STRUCTURE within one run — not a death-recovery mechanic. Death still ends the run exactly like today.

B

Switch to checkpoint resume

Death respawns you at the last checkpoint within the same attempt. This is a real, deliberate departure from D1 — a mode change, not an addition.

C

Hybrid — checkpoints exist, but death still ends the run

Checkpoints matter for PACING/SAVE-AND-QUIT and maybe partial reward banking, but a death mid-run is still final, matching D1. (I'll explain what a "checkpoint" even means under this option if you pick it.)
